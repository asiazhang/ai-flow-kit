## 目标

只分析当前 `HEAD` 相对主干的**已提交变更**。

## 执行流程

### 1. Evidence：收集证据

在目标仓库中，使用当前已加载 Skill 的目录作为 `<skill-dir>`，执行：

```bash
bash "<skill-dir>/scripts/collect-evidence.sh"
```

脚本同步 `origin`、选择主干基准，并输出带区段标记的提交列表（不含同步主干的合并提交）、diff 统计和完整 diff。分支已合入主干时，脚本自动回退到合并前的主干作基准并标记 `BRANCH_MERGED=true`。所有数据从脚本输出读取，比较基准以其中的 `BASE_REF` 为准。

脚本失败时报告错误并停止。脚本对仓库只读，但 `git fetch --prune origin` 会更新本地远程跟踪引用。

**完成条件**：已成功读取 `COMMITS`、`DIFF_STAT` 和 `DIFF` 区段；无已提交文件变更时，已读取 `SUMMARY_STATUS`。

### 2. Reason：提炼修改意图

只根据提交信息和 diff 提炼意图。阐述遵循**意图优先**：解释"为什么要改"重于描述"改了什么"。无法确认的业务背景标为"推测"。

**完成条件**：每个摘要判断都能回溯到提交信息或 diff。

### 3. Report：按固定格式输出

严格输出以下三个部分，顺序固定：

```text
**核心目标**：一句话概括最高层级目标。

**变更原因与改进**：
- **关键词**：说明修改前存在的痛点和为什么要改。
- **关键词**：补充改动如何解决该痛点及带来的影响。

**关键技术点**：一句话概括涉及的模块、架构调整或技术手段。
```

格式规则：

- 核心目标只写**一个**最高层级目标。分支包含多个并列主题时，提炼它们共同的更高层意图；无法合并时选择主要主题，其余主题放入“变更原因与改进”。不用“同时”“并”等连接词在核心目标中罗列多个目标。
- 每条“变更原因与改进”以加粗关键词开头。
- “关键技术点”保持一句话，只概括模块、架构调整或技术手段，不罗列文件名、行数或 diff 统计数字。

没有已提交文件变更时，仍输出三部分；在“核心目标”中明确“相对 `<BASE_REF>` 没有已提交文件变更”。`BRANCH_MERGED=true` 时，在“核心目标”中注明“分支已合入主干（`<MERGE_COMMIT>`）”。

**完成条件**：输出与模板、格式规则及空变更规则逐项一致。
